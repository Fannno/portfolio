QWQ 監規餘

Quick Wallet Query — 個人收支管理與日常記帳系統

一套支援跨裝置同步的個人收支管理系統。目前對應 114_web_endterm_project 儲存庫的實作版本採用 MERN Stack 前後端分離架構（React、Node.js、Express、MongoDB Atlas），具備 JWT 身分驗證與每日收支自動彙整； 後續規劃逐步重構為 C# / .NET MVC 與 SQL Server 關聯式資料庫架構，強化型別安全與企業級系統維運結構。

專案背景與開發動機

本專案源於 114 學年度網頁程式設計期末專題，旨在解決日常個人記帳在手機與桌面電腦之間難以同步、 且純靜態頁面缺乏使用者帳號隔離與雲端資料持久化的問題。

第一階段以 MERN Stack 完成全端實作與雲端部署後，結合實習期間累積的企業級系統開發經驗， 進一步規劃將系統朝向 C# / .NET MVC 與 SQL Server 架構重構，讓財務帳務資料具備更嚴謹的關聯式結構與分層設計。

專案目標

  • 前後端分離與雲端儲存：建構獨立前端 SPA 與 RESTful API 後端，達成跨裝置帳務即時同步。
  • 無狀態身分驗證與資安防護：透過 Bcrypt 雜湊保護與 JWT 中介軟體確保每位使用者的財務資料安全隔離。
  • 高效能日期彙整檢視：於前端以單次遍歷分組演算法即時計算每日收支小計並依日期降冪呈現。
  • 技術架構演進（後續規劃）：規劃以 C# / .NET MVC 與 SQL Server 進行重構，深化關聯式帳務查詢與預算規則驗證。

核心功能與特色（現有 MERN 版本）

帳號註冊與 JWT 驗證

支援使用者註冊與登入，前後端雙重執行 Regex 格式驗證，憑證經 Bcrypt 加鹽雜湊儲存， 並以 Bearer Token 保護私有帳務路由。

完整收支 CRUD 操作

提供收入與支出項目的新增、查詢、編輯與刪除功能，每筆紀錄皆嚴格綁定登入使用者識別碼。

每日自動分組與小計

自動將扁平的交易陣列依日期歸類為獨立日期卡片，由新到舊排序並即時加總當日收支淨額。

響應式跨裝置介面

前端部署於 GitHub Pages，針對手機與桌面瀏覽器調整表單與列表排版，支援隨時隨地記錄開銷。

系統架構與技術演進路線

以下左側為目前已部署上線的 MERN Stack 三層式雲端架構；右側則標註後續規劃重構之 C# / .NET MVC + SQL Server 目標架構方向（目前為規劃階段）。

開發過程與實作歷程

現有版本（MERN Stack）實作重點

  • frontend/：以 React 負責登入註冊與儀表板元件化開發及 Virtual DOM 更新，並透過 Vite 提供開發伺服器、打包建置與 VITE_API_URL 環境區分。
  • Hash Map 日期分組：單次遍歷資料庫回傳陣列建立日期鍵值表，同步計算當日總額並執行降冪排序。
  • backend/middleware/：實作 authMiddleware 驗證請求標頭之 Bearer Token，隔離不同使用者的帳務存取權限。
  • backend/models/：透過 Mongoose 定義 User 與 Record Schema，確保驗證資訊僅存雜湊值。

後續重構方向（C# / .NET MVC + SQL Server）

在完成課程專題的 MERN 實作後，結合日常學習與實習所使用的 C# (.NET MVC) 與 SQL 技術棧， 規劃將「QWQ 監規餘」作為後續重構練習標的（目前尚未完成重構）。

  • 重構目的：將單純收支紀錄擴展為包含預算上限設定與剩餘額度查詢的關聯式系統。
  • 架構規劃：導入 SQL Server 進行交易完整性控管與多條件財務報表查詢。

遇到的問題及解決方式

1. 環境設定檔管理與資料庫連線安全

問題：開發初期曾將含資料庫連線設定的環境檔誤納入版控提交，觸發儲存庫安全掃描提醒。

解法：立即於 MongoDB Atlas 輪換連線憑證，將敏感設定檔加入 .gitignore 排除，並改由 Render 雲端環境變數面板安全注入。

2. 前後端分離部署之 CORS 跨域攔截

問題：前端部署於 GitHub Pages、後端部署於 Render 時，跨網域 API 請求與 Preflight 被瀏覽器阻擋。

解法：在 Express 後端設定 cors 中介軟體白名單明確允許前端網域與 Authorization 標頭，並以 VITE_API_URL 統一切換環境路徑。

3. Render 免費方案休眠導致首次請求延遲

問題：Render 免費方案伺服器在閒置 15 分鐘後會自動進入休眠（Spin Down），喚醒時請求需等待約 30 至 60 秒。

解法：於前端加入載入等待提示避免使用者重複送出表單，並在 README 與展示說明中明確標註冷啟動特性。

4. 扁平交易陣列的重複篩選效能問題

問題：後端回傳的紀錄為扁平陣列，若每次渲染皆使用巢狀迴圈依日期比對，當筆數增加時邏輯複雜度高。

解法：改用 Hash Map 進行一次 O(N) 遍歷即可同時完成分組與每日收支小計，再配合 React Virtual DOM 執行局部畫面更新。
